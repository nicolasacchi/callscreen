Callscreen is a mature, well-built single-operator multi-tenant call screener. The webhook trust boundary is solid (correct Telnyx Ed25519 verification with a 5-minute drift window, timing-safe token comparisons, an SSRF host-allowlist on recording downloads, and strong LLM prompt-injection defenses), multi-tenant isolation in the admin UI is genuinely tight (every admin controller scopes through viewing_tenant; no IDOR; tenants cannot self-escalate to admin), the unit suite is disciplined (~480 tests with real WebMock stubbing), and supply-chain hygiene is good (lockfile checksums, a pinned base image, Dependabot).

The real weaknesses live at the edges: deploy/ops hardening (no SQLite backups, Sentry disabled in production, an 8.5 GB host venv baked into the image, committed secret defaults in the compose file), a few silent failure modes in the asynchronous screening path (a Whisper outage misclassifies real callers as “said nothing”; recording-download 5xx dead-letters with no operator notification), one broken front-end import (Turbo is never loaded, so logout is broken and every confirmation dialog silently no-ops), and accumulated dead code from the TeXML→Voice-API rewrite. The core call state machine lives in a 747-line god controller that is correct but hard to change safely.

The 5 highest-stakes lenses were adversarially verified against the source (false positives dropped, several severities corrected downward). The other 7 lenses were not auto-verified — the background runner was killed during an idle gap — but every high-impact item from them was re-verified by hand against the code before landing in the roadmap.

Per-lens health

Security & webhook trust boundary
10 findings verified		The webhook trust boundary is generally well-constructed for a single-operator service: Telnyx Ed25519 verification is correct (proper SPKI DER wrapping, 5-minute timestamp drift window giving real replay protection, fails closed when the public key is missing or malformed), all token comparisons use ActiveSupport::SecurityUtils.secure_compare, the e2e inspector and X-E2E-Now time injection are genuinely invisible when SYNTHETIC_WEBHOOK_TOKEN is unset, SSRF in RecordingDownloader is constrained by a host allowlist that blocks internal targets, and the LLM classifier has solid prompt-injection delimiters plus control-char stripping. Brakeman runs clean (3 ignored warnings, all still valid). The notable gaps are: no Content-Security-Policy at all (the initializer is 100% commented out), the 14-day ntfy action token rides in a `t=` query param that escapes filter_parameter_logging and lands in request logs, Rack::Attack throttles run on a per-process in-memory cache (no shared/persistent store) so they reset on deploy and don't coordinate across Puma workers, and the Ed25519 verifier has no nonce/event-id replay cache (timestamp window only). None are critical for this threat model, but the CSP gap and the logged action token are worth fixing.
Multi-tenant isolation & authorization
7 findings verified		The admin UI is generally well-isolated: every per-resource admin controller routes writes/reads through `viewing_tenant` (which falls back to `current_tenant` for non-super-admins and only honors `?tenant_id=` for `super_admin?`), the two operator-only controllers (`TenantsController`, `SettingsController`) gate on `require_super_admin!`, `ProfilesController` never permits `:admin` so a tenant cannot self-escalate, and the public greeting/recording/ntfy-action surfaces each have their own correct trust boundary (regex+allowlist, per-tenant call scope, signed token). The one real cross-tenant hole is the `/e2e/*` inspector: it is gated only by a single flat `SYNTHETIC_WEBHOOK_TOKEN` (no per-tenant scoping), that token is enabled in the production compose with a hardcoded fallback value committed in `compose.yml`, and the endpoints enumerate any tenant/contact/call by slug/phone/call_control_id with full attribute dumps. Remaining items are defense-in-depth (unscoped `Contact.where(id:)` in costs, super-admin recording bypass, default-tenant == super-admin fallout) rather than exploitable today.
Reliability, error handling & idempotency
12 findings self-verified hi-impact		The live call path is generally well-thought-out for idempotency: `call_control_id` has a unique DB index, `handle_recording_saved` and `finalize_billing` have explicit idempotency guards, and the controller always returns 200 so Telnyx never replays a whole flow on a transient 5xx. The voice/phrase rotation cursors use `with_lock` correctly. However there are several real failure modes for a single-operator service: (1) the `recording.saved` idempotency guard keys on `recording_url.present?`, which breaks if Telnyx ever delivers the event without a URL, causing a double goodbye/ScreeningJob; (2) the spam path can double-notify because `apply_spam_response` enqueues NotifyJob AND Screening.finalize enqueues it again on certain transitions; (3) the job `retry_on` lists are miscalibrated against how HTTParty actually signals failure — Whisper outages are swallowed to `nil` and silently misclassify as "caller said nothing", while RecordingDownloader 5xx raises a bare RuntimeError that bypasses retry entirely and dead-letters after marking the call `failed` with no notification to the operator.
Performance, latency & DB efficiency
8 findings verified		The call hot path is mostly well-architected: heavy work (Whisper, LLM, render) is correctly pushed into Solid Queue jobs on a `:default` queue that is intentionally separated from `:rendering`, and the controller closes the caller's leg promptly via `play_goodbye` + async `ScreeningJob` so callers never wait on transcription/classification. The single real latency risk on the synchronous webhook path is the blocking `RailsdavContactsClient.lookup` (3s timeout) inside `call.initiated`, which sits in front of `cc_client.answer` and competes with only 3 Puma threads. On the DB side the dataset is tiny (single operator), so most things are fine, but there are a few concrete inefficiencies: a genuine N+1 in the Tags index, a duplicated full-window scan in the Costs chart, an over-broad pluck-into-IN pattern in the Phrases index, and a missing composite index for the time-windowed cost/dashboard aggregations. None are emergencies, but the railsdav blocking call and the Costs double-scan are the two worth acting on.
Architecture & separation of concerns
10 findings verified		The codebase is mostly well-factored at the service layer (PhrasePoolResolver, LanguageResolver, RailsdavContactsClient, CallControlClient, SpamClassifier are cohesive and reasonably testable), and the deliberate queue split + per-call voice caching show real design care. The dominant structural problem is TelnyxController: a 747-line, 34-method god object that fuses HTTP-webhook auth, tenant resolution, the entire call-flow state machine, the policy/spam-gate pipeline, voice+phrase selection, and audio-URL construction into one class with no injection seam for the Telnyx client. The call lifecycle is an implicit FSM expressed as scattered `case call.flow_state` branches with 7 dead states declared in the enum, and there is a config-split smell where 9 of 13 global Setting keys are exact duplicates of per-tenant Tenant columns. None of these are correctness bugs today, but they make the highest-traffic, highest-risk part of the system the hardest to reason about and change safely. The three highest-leverage refactors: (1) extract the policy pipeline from handle_initiated into a CallPolicy service; (2) extract audio/voice/phrase selection into an AudioResponder/VoiceSelector so playback helpers leave the controller; (3) make the call-flow FSM explicit and prune the dead flow_states.
Data model, schema & migrations
11 findings verified		The schema is generally sound for a single-server SQLite phone screener: foreign keys are declared, join tables are correctly uniquely-indexed, the partial-unique indexes on dedicated_number and default_tenant are clever and correct, and money columns use sensible decimal(12,8). The dual status(integer)/flow_state(string) design on calls is justified (classification outcome vs leg-lifecycle FSM), not a defect. The main weaknesses are: a very wide tenants table that mixes auth, voice, phrase-rotation, time-of-day and spam config in ~60 columns (a maintenance/cohesion liability but low operational risk at this scale); several redundant single-column indexes that are dead because all real queries are tenant-scoped; a couple of indexes that are strict prefixes of composite indexes; and some nullability/default choices (tenants.name, tenants.slug, calls.from_number) that don't match the application's assumptions. No data-loss or integrity-corruption bug was found.
Code quality, duplication & simplification
14 findings self-verified hi-impact		The codebase is in genuinely good shape for a single-operator multi-tenant service: rubocop-omakase is essentially clean (15 trivial auto-correctable offenses), services are small and single-purpose, the controller FSM is well-commented, and several past refactors already consolidated duplication (LanguageResolver, apply_spam_response). Net realistic LOC reduction is modest (~120-180 lines) but improves clarity in the highest-traffic files.
Test coverage & quality
11 findings self-verified hi-impact		The unit suite is genuinely strong for a single-operator service: ~480 test methods across 48 files, real behavioral assertions, disciplined WebMock stubbing of every external call (Telnyx, Whisper, Moonshot, railsdav, ntfy), and excellent edge-case depth in the highest-risk areas — TelnyxController dispatch (58 tests covering every flow_state transition, tenant resolution, all spam_response_modes, voice rotation race, idempotency), ScreeningJob classification/auto-blacklist, and the 7-tier PhrasePoolResolver. No coverage measurement exists. Overall health: good core, weak perimeter and CI integration.
Ops, deploy & observability
10 findings self-verified hi-impact		For a single-operator service this deploy is mostly sane (jemalloc, non-root, WAL SQLite, in-Puma Solid Queue, separated render queue, healthcheck wired both in Dockerfile and compose). But three things undercut it badly: (1) the SQLite databases that hold the ENTIRE business state — call history, tenants, contacts, blacklist/whitelist rules, audit log — have NO backup of any kind, so a disk/volume loss is total and unrecoverable; (2) Sentry is dead in production because no SENTRY_DSN is set in the compose env, so all the PII-scrubbing/request-id/exception-capture machinery is a no-op and the operator is flying blind on errors; (3) the 8.5 GB host .venv is not in .dockerignore and is swept into the image via COPY . ., bloating the build context and final image. Python TTS/render scripts & shell boundary
9 findings self-verified hi-impact		The Ruby->Python boundary is fundamentally sound: both jobs use Open3.popen2e(*cmd) with argv arrays, so there is no shell and no command/argument injection — user-authored phrase text (text_it/text_en) is passed as discrete argv tokens that argparse cannot reinterpret as flags. The notable hole is the `voice` axis: `voice_rotation_voices` is unvalidated free-text that flows verbatim into Pathname#join for the WAV output path and into the Python --voice/--out, allowing path traversal outside storage/greetings by an authenticated tenant. TTS output is also non-deterministic (no seed) for the Chatterbox paths.

SEC-1 ntfy action token (14-day, mutating) leaks into request logs via unfiltered `t=` query param mediumconfirmed

config/initializers/filter_parameter_logging.rb:6-10 · app/services/ntfy_notifier.rb:60-62 · app/services/ntfy_action_token.rb:7-15 · app/controllers/ntfy_actions_controller.rb:17 · config/routes.rb:13-17

Problem. NtfyActionToken issues a MessageVerifier-signed token with EXPIRES_IN = 14.days that authorizes a state-changing action (whitelist a number, mark spam, report a number to the global railsdav spam feed). NtfyNotifier embeds it as a URL query param `?t=<token>` (ntfy_notifier.rb:60-62), and NtfyActionsController#perform! reads it from `params[:t]`. filter_parameter_logging.rb only filters params matching `:token`, `:_key`, etc. The single-letter param name `t` matches none of these partial filters (it does not contain the substring "token"), so at the default production log_level of "info" Rails writes the full token into the `Processing ... Parameters: {"t"=>"..."}` log line for every button tap. Any operator/log-aggregation reader (or anyone who later gets STDOUT/container logs) recovers a credential that stays valid for 14 days and can be replayed to whitelist arbitrary callers or push a number into the shared spam DB. Contrast: the fallback `?token=` and `?synthetic_token=` params ARE filtered because their names contain "token".

Fix. Add `:t` to filter_parameter_logging.rb (or rename the param to `:token` so the existing filter catches it). Shorten EXPIRES_IN to ~48h. Note the per-call scoping already limits impact, so this is medium not high.

Evidence. config/initializers/filter_parameter_logging.rb:6-10 lists `:token` but not `:t`. Rails' ParameterFilter does substring matching, and the literal `t` is not a substring of any listed key in the way that filters it (a 1-char key `t` does not match `:token` — matching is key-name-contains-filter, so param 't' is filtered only if 't' equals/contains a filter term; 'token' contains 't' but 't' does not contain 'token'). NtfyNotifier.build_actions embeds `?t=#{tok_w}` (ntfy_notifier.rb:60-62) and NtfyActionsController#perform! reads params[:t] (ntfy_actions_controller.rb:17). EXPIRES_IN = 14.days (ntfy_action_token.rb:7). production.rb:34 log_level defaults to 'info', so the token lands in the `Parameters:` log line. Verdict confirmed; downgraded from high to medium: the token is an authenticated-action credential but its blast radius is one specific call_id (payload[:call_id] is bound and checked at ntfy_actions_controller.rb:19), so a leaked token only lets an attacker whitelist/spam/global-report THAT one call's from_number, not arbitrary callers. The finding's claim 'replayed to whitelist arbitrary callers' is overstated — it is scoped to the single call the token was minted for. Log exposure of a 14-day mutating credential is still real and worth fixing.

SEC-3 Rack::Attack throttles run on a per-process in-memory store with no shared/persistent cache lowconfirmed

config/initializers/rack_attack.rb:1-16 · config/environments/production.rb:1-75 · config/application.rb:21-41

Problem. rack_attack.rb defines three throttles (telnyx/ip 60/min, admin login by IP 10/5min, admin login by email 5/20min) but never sets `Rack::Attack.cache.store`, so it defaults to `Rails.cache`. No solid_cache gem is in the Gemfile and no `config.cache_store` is set in production.rb or application.rb, so Rails.cache falls back to a per-process memory store. Consequences: (1) every throttle counter resets to zero on each deploy/restart (frequent here — migrations run on container start per CLAUDE.md); (2) if Puma/Thruster runs more than one worker process, each worker keeps an independent counter, multiplying the effective limit by the worker count; (3) counters are unbounded across the fleet of one but still inconsistent. The credential-stuffing throttle on admin login (the security-relevant one) is therefore softer than it reads and is wiped on every deploy. For a single-server box this is a degradation, not a bypass, but the login throttle is the thing actually protecting the operator account.

Fix. Optionally set Rack::Attack.cache.store = ActiveSupport::Cache::FileStore.new(Rails.root.join('tmp/rack_attack')) so counters survive restarts. Low priority because Devise lockable (maximum_attempts=5, unlock_in=1h, DB-backed) is the durable account-protection control.

Evidence. rack_attack.rb never sets Rack::Attack.cache.store. grep across Gemfile/application.rb/production.rb/initializers shows NO solid_cache gem and NO config.cache_store, so Rails.cache falls back to MemoryStore. Reliability, error handling & idempotency

The live call path is generally well-thought-out for idempotency: `call_control_id` has a unique DB index, `handle_recording_saved` and `finalize_billing` have explicit idempotency guards, and the controller always returns 200 so Telnyx never replays a whole flow on a transient 5xx. The voice/phrase rotation cursors use `with_lock` correctly. However there are several real failure modes for a single-operator service: (1) the `recording.saved` idempotency guard keys on `recording_url.present?`, which breaks if Telnyx ever delivers the event without a URL, causing a double goodbye/ScreeningJob; (2) the spam path can double-notify because `apply_spam_response` enqueues NotifyJob AND Screening.finalize enqueues it again on certain transitions; (3) the job `retry_on` lists are miscalibrated against how HTTParty actually signals failure — Whisper outages are swallowed to `nil` and silently misclassify as "caller said nothing", while RecordingDownloader 5xx raises a bare RuntimeError that bypasses retry entirely and dead-letters after marking the call `failed` with no notification to the operator.

Problem. WhisperClient#transcribe rescues every error (HTTP 5xx, timeout, connection refused) and returns nil (whisper_client.rb:26-31), never raising.
