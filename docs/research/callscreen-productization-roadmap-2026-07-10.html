Callscreen Productization Roadmap — July 2026

The engineering is ahead of the product: to become a real service, Callscreen needs an ops floor (off-box backups, canary), a self-serve lifecycle (email, invitations, onboarding wizard), and only then billing — in that order.

2026-07-10 · status:open · project:callscreen

The strategic call: who is this for?

The carrier-forwarding architecture is the moat. A customer keeps their number and their phone; activation is one MMI code (**61*<screener>#) — no porting, no app on the call path, works on any handset. That favors one segment decisively:

SegmentWillingness to payFit
Italian professionals & micro-businesses (lawyers, doctors, artisans, agents) drowning in spam and missing real calls€10–30/mo — a missed client costs moreTarget. Screening + voicemail + transcript + instant push is a "segretaria virtuale" at 1/50 the cost
Italian consumers annoyed by spam€0–3/moLater. Mass GTM, thin margins, support burden
Friends & family€0Current state; good beta pool

Recommendation: invitation-only beta of 5–10 real professionals at €0 for a month (validates onboarding + catch-rate), then Stripe at ~€9.90/mo personal / ~€19.90/mo professional (voice clone, rules, priority). Do not build open self-signup first — invitations keep the abuse surface tiny while the lifecycle plumbing matures.

Unit economics

Per tenant/month at 100 screened calls averaging 90 s: Telnyx DID ~$1.00 + inbound ~$0.45; Moonshot classification ~$0.02 (non-reasoning 8k, ~2 s/call); Whisper + TTS self-hosted ≈ $0. Marginal cost ≈ $1.50/tenant → ~93% gross margin at €9.90. The binding constraint is not cost, it's onboarding friction and trust.

Phase 0 — protect what exists (this week)

One host holds everything; the ops audit's verdict was blunt: the app layer is mature, the host perimeter is not.

  • Off-box backup — the single riskiest gap. db:backup (WAL-safe VACUUM INTO) writes to storage/backups/ on the same bind mount as production.sqlite3, and compose-host/backup/dump-all.sh covers other host services but has zero callscreen entries. A disk failure today is total, unrecoverable loss of all tenants, calls, audit history, and voicemail audio. Add callscreen to the borg job; rehearse a restore.
  • Whisper sidecar: unpinned :latest-cpu image, no healthcheck, no depends_on. A silently broken Whisper degrades every screening to "unknown". Pin by digest + healthcheck + startup ordering.
  • Proactive detection: external uptime probe on /up (alert channel independent of ntfy — the watchdog currently self-routes to the same ntfy that could be the failed component) + a daily bin/synthetic_call canary cron. Today, regressions are only caught reactively.
  • Python TTS supply chain: torch/chatterbox/kokoro unpinned, no lockfile, no pip audit in CI. Lock with uv, add the pip ecosystem to Dependabot.

Phase 1 — a stranger can be onboarded (2–3 weeks)

Today a new tenant requires the operator to: create the account with a typed password, set dedicated_number, hand-walk carrier MMI codes (the in-app instructions render the operator's own Modena number for every tenant), explain the ntfy app, and run bin/clone_render on the host. Each is a fixable product gap:

  • Email foundation first — everything else depends on it. The app sends no email at all: the mailer host in config/environments/production.rb is literally example.com, the Devise sender in config/initializers/devise.rb is please-change-me@example.com, and :recoverable/:confirmable are off in app/models/tenant.rb (a forgotten password is an operator ticket). SMTP creds from operator secret store → compose env, enable password reset, then confirmable.
  • Invitation flow + onboarding wizard. Invite email → set password → wizard: (1) pick notification channel, (2) see your forwarding number, (3) carrier picker (TIM/Vodafone/WindTre/Iliad) rendering the correct MMI codes from tenant.dedicated_number, (4) a "verify forwarding" button that watches for the test call end-to-end — the e2e inspector plumbing to build this already exists.
  • Email as a notification channel. ntfy requires installing an app and pasting a topic URL — a real barrier for the target segment. A per-tenant channel enum (ntfy|email|both) routed in app/jobs/notify_job.rb, with voicemail transcript + secure recording link, makes notifications work for anyone with a mailbox. (Web push via the existing public/sw.js PWA shell is the better long-term answer; it's phase 3.)
  • Finish Italian i18n of the admin console. The primary market is Italian; the console is ~80% hardcoded English (55 English headings; app/views/admin/profiles/edit.html.erb, rules, phrases, costs have zero t() calls, and config/locales/it.yml covers a fraction of config/locales/en.yml). Caller-facing audio is already fully bilingual via app/models/greeting_catalog.rb — the console must match.
  • De-hardcode the single-operator assumptions: per-tenant forward_back_number required at onboarding (no silent inheritance of ENV["FORWARD_NUMBER"]), ntfy ENV fallback restricted to the default tenant, tenant-editable time_zone/tod_*/spam_response_mode (currently console-only), and in-container voice-clone rendering so the flash message stops telling users to run a host script.

Phase 2 — they can pay (2–4 weeks)

  • Stripe Checkout + customer portal + Stripe Tax (EU VAT/SCA handled for you). A small Plan model; webhook sets tenant.plan and tenant.active. Non-payment degrades gracefully: screening off, plain forward-through on — never dead air for the tenant's callers.
  • Quota enforcement on metering that already exists. Per-call billable_seconds, Telnyx and Moonshot cost columns are recorded today via app/lib/pricing.rb; app/controllers/admin/costs_controller.rb reports them. Add monthly caps per plan with a usage bar and soft-degrade past quota.
  • Automatic number provisioning. Telnyx's number search/order API can buy a DID and set dedicated_number at signup — removing the last manual provisioning step.
  • Public surface + legal. There is no marketing page (root redirects to login). Landing + pricing + privacy policy + DPA. As a service you are a GDPR data processor for third-party callers' audio: the greeting should disclose recording, retention defaults (30 days, already implemented in CleanupRecordingsJob) must be stated, and a data-subject export/erasure runbook written.

Phase 3 — product depth bets (after first paying users)

  • Web push in the PWA — the service worker shell exists; add a push handler + VAPID + a PushSubscription model, and ntfy becomes the power-user option instead of the requirement.
  • Live transfer for verified-legit callers — bridge states (transfer_dialing/bridged) already exist; "sounds legitimate → ring the tenant now, else voicemail" is the strongest professional-tier feature.
  • Daily digest email — screened/blocked/voicemail summary; cheap retention driver.
  • Shared spam intelligence as network effect — the railsdav-backed cross-tenant spam DB and allow-propagation already exist; every new tenant makes screening better for all. Surface it ("blocked for 214 users this week").
  • Calendar-aware screening — CalDAV is in the stack; "in a meeting → screen harder, after hours → voicemail only."
  • Per-tenant outbound webhooks/API — push screened-call events into a CRM; opens the door to agencies managing multiple tenants.
Non-goalA native Android/iOS call-screening app. The zero-app carrier-forwarding path is the differentiator; an app on the call path re-enters a market Google/Truecaller own.

Scale posture

Do not re-platform for scale now. The webhook path is light; SQLite WAL + single-writer with 3 default-queue threads comfortably serves ~50–100 tenants at 10–50 calls/day each. Real ceilings, in the order they will appear: Whisper CPU throughput on concurrent calls (medium model ≈ real-time on CPU — first knob: JOB_CONCURRENCY, second: GPU or a smaller model for screening), TTS renders sharing the box, then the single-node deploy blip. When off-box durability is built (phase 0), prefer Litestream streaming replication — it solves backup and becomes the stepping stone to a warm standby, without leaving SQLite.

Metrics that decide "is it working"

  • Activation: % of invited tenants whose forwarding-verification call succeeds (wizard step 4) within 48 h.
  • Catch quality: operator-correction rate — mark_spam/mark_legit actions ÷ screened calls (both already audit-logged). Below ~5% corrections is a sellable screener.
  • Engagement: screened calls per tenant per week (current baseline: 10/wk across 2 tenants).
  • Reliability: watchdog-quiet days per month; canary pass rate.
  • Revenue truth: margin per tenant from the existing per-call cost columns vs. plan price.

Verification & rollback

Each phase lands behind the existing safety net: 581-test unit suite + brakeman + rubocop + coverage floor in CI, the 7-scenario live e2e suite (rake e2e:run) against prod with the suppressed-notification e2e tenant, and bin/synthetic_call --watch for one-shot verification. Rollback: single-container git revert + rebuild; DB restores from the boot-time pre-migration snapshot (off-box after phase 0). Billing enforcement ships behind a flag so suspension logic can be disabled without a deploy.
